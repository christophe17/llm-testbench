# ADR 011 — Evaluation harness: retrieval first, reproduced before trusted

- **Date**: 2026-11-05
- **Status**: accepted

## Context

Phase 2 builds the harness that every later phase reports through. Its first block is
retrieval (2.1), validated against published scores (2.2), with confidence intervals (2.4)
and a regression guard (2.7). Until now the only numbers of the testbench came from `mteb`,
which evaluates a model on a corpus, not our system: no chunking, no pgvector, no index
settings. Seven decisions had to be taken; generation metrics and the judge get their own
ADR with step 3.

## Decisions

**1. A published score is reproduced under its own conditions before our system is
measured.** A harness that prints 0.71 where the literature says 0.74 can be wrong in the
metric, the join, the embedding or the search; nothing tells which. So each dataset gets
two kinds of arms. *Reproduction* arms copy the conditions of the published number (whole
documents, exact search, the model's query instruction, the pinned weights) and must land on
it. *System* arms measure the phase 1 pipeline as built (recursive chunks, HNSW). The gap
between the two is then a property of our choices, measured, and not a doubt about the
harness. Rejected: comparing the system arm directly with the literature, which mixes both.

**2. Retrieval metrics are pure functions on a ranking, with the conventions of
`trec_eval`.** Recall@k, precision@k, MRR@k, nDCG@k (`eval/metrics/retrieval.py`), linear
gain, named like `mteb` names them. Rejected: depending on `pytrec_eval` at run time (a C
extension for sixty lines of arithmetic, and it hides what the notebook must explain); it
stays as a cross-check in the tests.

**3. A retriever answers at the document level.** The datasets judge documents, the index
stores chunks. `Retriever.retrieve` returns each document once; the dense retriever folds
the nearest chunks into documents by their best chunk, in SQL
(`PgVectorStore.search_documents`), and the search mode is explicit: `exact` (index off,
every vector compared) or `hnsw` with pgvector's settings. Rejected: folding in Python
from a chunk-level top-k, which cannot be exact and silently inherits the HNSW bound (never
more rows than `hnsw.ef_search`, 40 by default, whatever the `LIMIT`).

**4. BM25 enters as a harness arm, through `bm25s`** (question left open on 2026-11-04).
Options: (a) `bm25s` in process, with the preprocessing of `mteb/baseline-bm25s`; (b)
Postgres full-text search. (b) is not BM25: `ts_rank` has neither IDF saturation nor BM25's
length normalization, so it cannot be compared with any published BM25 number, and the
extensions that implement real BM25 in Postgres are not, to our knowledge, offered on RDS
(to be checked in phase 3). (a) reproduces the reference to four decimals. Where BM25 lives
in the API path is a phase 3 decision, on measurements.

**5. Open embedding models run in process, behind the embedding contract.** A new backend
kind, `sentence_transformers` (backend `hf`), embeddings only. Without it, no published
dense score can be reproduced through our pipeline: OpenAI publishes no per-task score.
Rejected: serving the model behind the OpenAI-compatible `local` backend (Ollama, TEI),
where converted weights and another pooling would make an exact reproduction a second
project. Three things a published score depends on are read from the registry, not from
code: the pinned revision, the query prompt, the vector size. `EmbeddingRequest` gains
`input_type` (`document` | `query`): asymmetric models are the norm, and the chat path now
says its question is a query. Amends ADR 006 ("two implementations": two for chat, a third
for embeddings).

**6. A run is a record, archived twice.** `RetrievalRun` carries the dataset as loaded, the
retriever as configured, the index build, the commit, each metric with a bootstrap interval
(10,000 resamples of the queries, seeded), latency percentiles, cost, the per-query scores
and the references with their source. The latest full run of each arm is a JSON file under
`data/results/runs/<suite>/`, versioned: it is the durable record, and its git history is
its history. Every run also goes to Postgres (`eval_runs`, `eval_query_results`): the
queryable history, which a recreated cluster loses. A run on fixtures, on a truncated
dataset or on simulated embeddings is never archived. Suites are declared in
`config/eval_suites.toml`; an arm builds the index it reads through the ingestion pipeline,
so a row is regenerated by its name.

**7. The regression guard has two levels, and says which is which.** `make eval-gate` runs a
suite in sample mode (fixtures, simulated embedder, about three seconds) against
`data/results/gate/baseline.json`; any drop fails the `pre-push` hook and the CI. It guards
code paths, not quality. Quality is guarded by the full run: `make eval` compares each arm,
query by query (paired bootstrap), with the archived run it replaces. Without a reachable
database the hook skips the dense arms and says so (a hook that fails whenever the cluster
is down gets bypassed); the CI requires them.

## Consequences

- Acceptance, met on 2026-11-05 on SciFact: BM25 0.6863 (`mteb`: 0.6863), bge-base-en-v1.5
  0.7404 (model card: 0.7404), text-embedding-3-small 0.7318 (`mteb`: 0.7313). NFCorpus,
  with graded judgments, checks the linear gain: BM25 0.321 against 0.325 for the paper's
  Anserini, bge-base-en-v1.5 0.3744 against 0.3739 on its model card.
- `bm25s` and `PyStemmer` join the main dependencies (with `scipy`): the image grows, for a
  retriever the API does not serve yet. Accepted until phase 3 decides.
- The `hf` backend needs the `bench` group (`torch`); CI never loads a model.
- The chunks of a source are shared by its indexes (ADR 007), so another chunking is
  another source key (`docs:scifact:whole`). The key carries what the schema does not:
  to be revisited with the experiment matrix of phase 3.
- Exact search is a sequential scan with a join: tens to hundreds of milliseconds per
  query here. It is a reference, not a serving path.
- The ingestion pipeline now reads the state of an index in two queries instead of two per
  document; an up-to-date index is verified in seconds.
- Accepted limit of the gate: it is bypassed by `--no-verify`, and a red CI on `main`
  records instead of preventing (ADR 008).
